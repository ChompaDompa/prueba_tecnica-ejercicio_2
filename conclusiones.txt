===============================================================================
 CONCLUSIONES Y HALLAZGOS - EJERCICIO 2 (API Demoblaze: signup / login)
===============================================================================

1. RESUMEN DE EJECUCION
-------------------------------------------------------------------------------
  Herramienta: Karate 1.5.1 + JUnit 5 + Maven (wrapper)
  Resultado  : 7 escenarios ejecutados, 7 exitosos, 0 fallidos
  Evidencia  : reports/karate-reports/karate-summary.html y reports/karate.log


2. ENTRADAS Y SALIDAS IDENTIFICADAS
-------------------------------------------------------------------------------
  Ambos servicios reciben un POST con header Content-Type: application/json y
  el body:
      { "username": "<texto>", "password": "<password codificado en Base64>" }

  Ejemplo: password "Softka2026*"  ->  "U29mdGthMjAyNio="

  +----+---------------------------------------+--------+-----------------------------------------------+
  | #  | Caso                                  | Status | Salida (body)                                 |
  +----+---------------------------------------+--------+-----------------------------------------------+
  | 1  | Signup - usuario nuevo                | 200    | ""  (string vacio)                            |
  | 2a | Signup - existente, mismo password    | 200    | {"errorMessage":"This user already exist."}   |
  | 2b | Signup - existente, otro password     | 200    | {"errorMessage":"This user already exist."}   |
  | 3  | Login - usuario y password correctos  | 200    | "Auth_token: <token>"                         |
  | 4a | Login - password incorrecto           | 200    | {"errorMessage":"Wrong password."}            |
  | 4b | Login - usuario inexistente           | 200    | {"errorMessage":"User does not exist."}       |
  | 4c | Login - usuario y password incorrectos| 200    | {"errorMessage":"User does not exist."}       |
  +----+---------------------------------------+--------+-----------------------------------------------+


3. HALLAZGOS
-------------------------------------------------------------------------------
  H1. Codigos HTTP no semanticos.
      Todos los casos, exitosos o de error, responden HTTP 200. El resultado
      solo se distingue leyendo el body. Lo esperado en una API REST seria:
        - Signup exitoso        -> 201 Created
        - Usuario ya existente  -> 409 Conflict
        - Credenciales invalidas-> 401 Unauthorized
      Impacto: los clientes y monitores que se basan en el status code no
      detectan errores. Las pruebas deben validar siempre el body.

  H2. Formato de respuesta inconsistente.
      Los errores devuelven un objeto JSON ({"errorMessage": ...}), pero los
      casos exitosos devuelven un string JSON ("" en signup y
      "Auth_token: ..." en login). El token viene concatenado dentro de un
      texto y no en un campo propio (ej. {"token": "..."}), lo que obliga al
      cliente a parsearlo manualmente.

  H3. Token de autenticacion predecible (riesgo de seguridad).
      El token devuelto es simplemente Base64(username + numero). Ejemplo:
        Auth_token: cWFfbG9naW5fMTc5NTEzOTM4OTY5M185OGYzM2Y4ZDE3OTU3Mzk=
        decodificado -> qa_login_1795139389693_98f33f8d1795739
      No es un token firmado ni aleatorio (como un JWT), por lo que podria ser
      adivinado o falsificado por un atacante.

  H4. Password "protegido" solo con Base64.
      Base64 es una codificacion, no un cifrado: cualquiera que intercepte el
      request puede decodificar el password. La proteccion real depende
      unicamente de HTTPS.

  H5. Enumeracion de usuarios.
      El login responde mensajes distintos para "Wrong password." y
      "User does not exist.", y el signup confirma "This user already exist.".
      Esto permite a un atacante descubrir que usuarios estan registrados.
      Recomendacion: usar un mensaje generico ("Usuario o password invalidos").

  H6. Errores ortograficos en mensajes.
      "This user already exist." deberia ser "This user already exists."

  H7. Inestabilidad intermitente del servicio / conexion.
      Durante las ejecuciones se observaron fallos esporadicos no
      relacionados con la logica de negocio: "Network is unreachable",
      "Connect timed out" y "Remote host terminated the handshake" (SSL).
      Se mitigaron forzando IPv4 y TLS 1.2 en la JVM
      (-Djava.net.preferIPv4Stack=true -Djdk.tls.client.protocols=TLSv1.2)
      y aumentando los timeouts a 30 s. Tras estos ajustes se lograron
      ejecuciones consecutivas 100% exitosas.

  H8. Sin validaciones aparentes ni limpieza de datos.
      El servicio permite registrar usuarios con nombres arbitrarios y no
      expone un endpoint para eliminarlos, por lo que cada ejecucion deja
      usuarios en la base de datos de demoblaze. Por eso las pruebas generan
      usernames unicos (prefijo + timestamp + UUID).


4. DECISIONES DE DISENO DE LAS PRUEBAS
-------------------------------------------------------------------------------
  - Datos dinamicos: cada escenario crea sus propios usuarios, por lo que
    las pruebas son independientes, repetibles y no dependen de datos
    preexistentes.
  - Reutilizacion: la creacion de usuarios esta en un feature helper
    (common/create-user.feature) invocado con "call" en scope aislado, y solo
    en los escenarios que realmente necesitan un usuario existente (menos
    llamadas a una API inestable, ver H7).
  - El duplicado de signup se prueba tambien con un password distinto, para
    confirmar que la unicidad se valida por username y no por la pareja
    username + password.
  - El login exitoso decodifica el Auth_token y verifica que pertenezca al
    usuario autenticado, no solo que exista un token.
  - El runner falla si no se ejecuta ningun escenario (por ejemplo, por un tag
    mal escrito), evitando falsos verdes en CI.
  - Lecciones de la automatizacion: las funciones definidas en
    karate-config.js no conservan variables externas (closures), y una
    expresion embebida '#(...)' que falla se envia como texto literal sin
    error. Por eso las transformaciones se hacen en un paso "def" explicito,
    que si falla detiene la prueba con un mensaje claro.
  - Scenario Outline para cubrir varias combinaciones de credenciales
    incorrectas con un solo escenario parametrizado.
  - Tags (@signup, @login, @smoke, etc.) para ejecutar subconjuntos.
  - Cada escenario imprime ENTRADA y SALIDA para dejar trazabilidad en el
    reporte, tal como lo pide el ejercicio.


5. CONCLUSION
-------------------------------------------------------------------------------
Los servicios de signup y login de demoblaze cumplen funcionalmente con los
cuatro casos solicitados: registran usuarios nuevos, rechazan usuarios
duplicados, autentican credenciales validas y rechazan las invalidas. Sin
embargo, el diseno de la API presenta debilidades importantes: codigos HTTP
no semanticos, formatos de respuesta inconsistentes y varias practicas de
seguridad debiles (token predecible, enumeracion de usuarios, password solo en
Base64). Se recomienda corregirlas antes de un uso productivo. Karate
permitio automatizar y documentar todos los casos de forma legible, repetible
y con reportes listos para compartir.
